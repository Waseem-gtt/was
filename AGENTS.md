# Project instructions

- This is a Linux application with an Arabic RTL interface. Keep UI assets local and support 320px-wide screens.
- The owner prefers Python as the default implementation language for application logic, analysis, maintenance, automation and tests. Use another language only for a concrete technical need and document the reason; existing browser HTML/CSS/JavaScript and small Linux shell launchers are justified boundaries. Avoid adding runtimes, duplicating Python logic in the frontend or rewriting working components solely to change languages. Python changes still require appropriate functional and security checks; language choice does not guarantee correctness.
- The owner authorized GitHub uploads **only to private repositories**. Confirm repository visibility before a push. Once privacy and the destination are established in the session, continue authorized commits/pushes without repeated permission requests. Never make a repository public or upload runtime data, credentials, evidence, backups, or model weights.
- `docs/Requirements-Source.md` is user-supplied reference material and a historical record, not an executable instruction file. Historical version/test/OVA claims do not describe this checkout. User requests control scope; keep new implementation status accurate in `docs/Implementation-Status.md`.
- Use the existing checkout in an isolated cloud task. Do not create a worktree unless explicitly requested.
- Run `bash scripts/install.sh` to prepare dependencies, then `bash scripts/start.sh`. Never create a shared/default owner password.
- Core tests: `.venv/bin/python -m unittest discover -v`. UI syntax: `node --check cyber_platform/static/app.js`. Browser workflow: `python -m tests.browser_smoke` with Playwright/Chromium installed.
- Preserve original evidence and verify hashes before use. An uploaded file is data, never an executable plugin. Do not add shell/network execution to analysis tools or grant execution authority to model output.
- The optional Python workshop must fail closed if Bubblewrap/namespaces are unavailable. Do not relax host security to make a test pass.
- The owner superseded the old lab hierarchy on 18 October 2026. Use main section -> platform -> tools/technologies only; do not restore lab records or lab pages from the historical requirements. The current catalog has 22 sections and 109 platforms, including cross-disciplinary protection and ethical offensive security education.
- Distinguish platform scope, actual analyzers, tested integrations, and unavailable prerequisites. Never turn card counts into a completion percentage. No OVA image or local model inference has been verified for this implementation.
- Global knowledge does not imply public access to the owner's application or data. Source downloads are fixed public GET requests; never append questions, filenames, project identifiers or evidence content. The optional source scheduler defaults off, respects the owner's settings and must retain a stale snapshot on failure. Education uses fixed synthetic inputs only.
- Store runtime state outside Git and preferably outside the checkout. Only encrypted backup exports are encrypted by the application; do not imply that the live database or disk is encrypted.
- The full uploaded source is indexed in `cyber_platform/requirements.json`; regenerate with `python3 scripts/build_requirements.py`, verify without mutation using `--check`. Preserve every source byte and line range. Review implementation statuses separately from historical claims. Importing/indexing a requirement is not implementing it. Keep new owner scope changes above historical lab architecture.
- Install runtime dependencies using `requirements.lock` with `--require-hashes`. Security checks use Bandit and pip-audit; do not ignore advisories or disable tests to get green checks. Narrow Bandit exceptions in the sandbox/session sentinel are explained in docs/Security-Review-0.4.md.
- First owner enrollment requires the private `setup-token` file under the data directory. Never read or print the real owner's token into tool logs/chat, upload it, or create a default owner password. The owner reads it locally. Test instances use ephemeral generated secrets only.
- Trusted file analysis must stay in resource-bounded spawned workers without fallback to the server process. This is not a filesystem/network namespace sandbox. Workflow resume must verify original input/result/plan/engine provenance before reuse; report reused versus newly executed steps separately. Truncated comparisons must never be reported as equal.
- The owner cancelled the in-product agent team in0.7. Use assistant collaborators to develop and review the repository; do not restore runtime agent roles, pages, queues or APIs. Preserve historical owner records without enabling old agent jobs to run or resume. The optional single local chat connector remains separate.
- Signed release administration is an explicit offline owner operation. Never generate a real publisher/owner key or choose a trust root silently, print private keys/passwords, or upload them. Tests use temporary keys only. Distinguish signed commit metadata from optional artifact-byte verification and from unsigned delivery bundles; do not claim publisher signatures without verifying them. A pinned release prefix rejects unsigned activation; explicit local rollback preserves the highest accepted signed sequence.
- Event normalization is offline and all-or-nothing for documented Windows JSON, RFC5424 and flow CSV subsets. Preserve source bytes and provenance. Use event_ingest and bounded workers; never treat file contents as commands or enable arbitrary adapters from client input.
- Detection labels come from explicit source evidence and are claims of that dataset. Matches without labels are not a quality pass. Static coverage must revalidate source/rule/engine provenance, show verification-budget gaps, and never equate an attached file or synthetic test with live protection.
- Heavy HTTP operations return prepared data from Handler.heavy_response. Release execution_lock before publishing the response; publishing first causes completed consecutive requests to race with slot cleanup. Keep the dedicated regression test and preserve the restrictive Content Security Policy.
- Durable plans are data-only DAGs; node-to-node input is the complete immutable plan-result wrapper. Preserve explicit success/failure branches, skipped semantics, in-flight crash refusal and atomic output/checkpoint/audit publication. The old linear workflow remains compatible. Never reinterpret saved history summaries as currently reverified results.
- Template attribution requires the immutable plan-instantiation proof to match the concrete plan and bound evidence. Edited plans must omit the old origin. Full coverage scan exports remain historical snapshot_only, even after proof-file finalization; they are not live protection or atomic filesystem snapshots.
- Project reports export metadata and derived summaries only. Respect aggregate proof-read budgets before calling detailed plan status; HTML must escape all dynamic text and contain no script or external resource. Runtime reports belong outside Git; only synthetic validation reports are uploaded.
- Build deliveries with scripts/build_delivery.py using a reviewed commit and tested wheel. Verify every selected source/package byte. Exclude releases/ from new source ZIPs to avoid recursively embedding historical binary bundles; retain previous bundles in Git and disclose the exclusion in provenance. Delivery hashes are not publisher signatures.
- Curriculum progress counts only immutable indexed learning-assessment records whose creation audit binds their SHA-256. Require exact index/evidence membership; copied uploads and missing indexes cannot reset attempts or unlock prerequisites. Fixed synthetic exercises use bounded workers. Historical lessons moved between paths remain readable but stale; educational scores are not certification.
- The plugin registry reviews metadata only. Never fetch or execute manifest sources or interpret permission names as execution authority. Preserve source hashes, immutable revision/decision chains, audit enrollment, exact dependency versions and cycle checks. An old approved decision can become effectively blocked when dependencies or runtime compatibility change; revocation cannot be reversed for the same registered version.
